# 写作与更新指南

写一条具体问题，留下可核对的依据，再决定结论状态。不要从批量填满栏目开始。

## 文章与实验是两类记录

`src/content/posts` 保存解释和判断；`src/content/lab` 保存某次具体执行。两者可以互相链接，但文章写得完整，不意味着实验已经发生。

文章使用 Markdown 或 MDX，包含发布/更新时间、系列、序号、难度、前置知识、环境、软件版本、结论状态、实际验证布尔值、执行者、可选代码仓库、证据与变更记录。完整示例见 `tcp-recv-message-boundary.mdx`。

结论枚举：`verified` 已通过实验验证、`source` 基于源码分析、`public` 基于公开资料推断、`pending` 尚待验证。`verified` 必须与 `realVerified: true` 一致，并至少提供一个证据文件；构建会检查这一点，但不会替作者判断证据是否有效。

`repository` 只填写对应代码仓库，不把个人主页伪装成代码地址。`verificationActor` 写实际执行者，不把工具执行写成自己已经独立掌握。

分类：`vpn`、`linux`、`crypto`、`pqc`、`performance`、`engineering`。系列按 `seriesOrder` 排列。发布日期使用首次实际发布日，updated对应真实修订，不自动每天刷新。

技术主线使用系统栈模块导航，在 `src/data/system-stack.ts` 的 `articles` 中加入真实文章 ID。原文选刊可通过 `scripts/import-reviewed-notes.py` 维护，并用 `--check` 核对正文。只填写真实发布和修订日期，详见 [内容主线与日期规则](内容主线与日期规则.md)。

## 一次手工更新

在博客目录复制文章模板，写好正文和元数据；未准备发布时设 `draft: true`。在终端依次执行 README 的检查和构建命令，再运行 preview。

- 检查正文、代码、表格与来源链接。
- 检查手机、深色模式、目录和证据下载。
- 在文章目录输入正文中特有的关键词，确认 Pagefind 能找到正文并跳转。
- 实验文章核对原始输出，写清没有覆盖的场景。
- 准备好后再提交到生产分支。GitHub Actions会构建、索引并发布。

`draft` 不会从 Git 仓库删除文件；绝不能把内部敏感材料放进去。RSS收录文章和实验日志摘要，既有链接尽量保持稳定。

## 技术内容块

MDX 中可导入 `../../components/blocks/Note.astro`，用 `kind` 选择“实验条件、关键证据、我的理解、容易误解、尚未确认、故障现场、源码入口、性能结论、安全边界”。内容放在组件内部。区别主要通过标题与细边框体现，只有故障/边界标签使用少量橙色。

Mermaid图导入 `Mermaid.astro`，传入 `source` 和说明性的 `caption`。生成在构建期完成，保留图示源文本方便审阅。当前测试的是基本时序图子集；需要 alt、复杂布局或其他图类型时先单独核对生成结果。静态 SVG 也可以放在 public，引用路径用 `pathFor`。

Markdown普通内部链接会在构建时增加部署基址。MDX里的HTML/组件链接使用 `pathFor('articles/slug/')`，不要重新写死根路径，避免项目站部署时断链。

首页按精选文章、连续阅读、旁支与小实验组织；同一文章不重复呈现。文章、主题和实验入口从内容集合生成。只给一篇文章设置 `featured: true`；简介在 `src/pages/index.astro` 手动维护，不从文件更新时间推断个人研究进展。

`description` 是摘要：写清问题、方法和范围。`takeaway` 是可由正文支持的要点，不能夸大验证程度。可选 `basis` 包含 `label`（依据名称）、`href`（公开标准或原始材料的链接）、`boundary`（未覆盖范围与执行者说明）。这些字段同时用于首页、文章目录和文章页，避免出现不同口径。未做实验时，明确标为资料阅读；不要为了呈现完整而填入虚构结论。

## 一次学习验收

对于AI协助完成的实验，本人至少走一次手工路径，解释关键结构，修改一个输入并诊断一次失败，再补对应学习记录。网站上的实验运行状态与个人掌握状态分开维护。
