读网关源码时，一个常见困难是函数越来越多，包却不见了。我现在更愿意先画出分叉，再沿着其中一条路读：**这个包的目的地是本机，还是另一台机器？**

本文取 Linux v6.6 的 IPv4 通用路径作源码坐标。它不覆盖所有驱动、桥接、XDP、隧道和硬件卸载分支，也没有声称在当前机器上跟踪过这些函数。

## 网卡之后，先有一段共同的路

在常见接收模型里，设备通过中断发出通知，驱动调度 NAPI，在预算内批量处理接收工作。NAPI 是处理机制，不是每个包都固定经过的一个函数。线程化 NAPI 和 busy polling 等模式也提醒我们：不能把某一张简图当成所有配置的事实。[Linux NAPI 文档](https://docs.kernel.org/networking/napi.html)

驱动交给通用协议栈的，通常是由 `sk_buff` 描述的数据及元信息。读路径时，除了内容，还要看设备、协议、校验和和路由相关状态。`skb` 不是一个可以随意等同于“线上原始帧”的普通字节数组。[sk_buff 文档](https://docs.kernel.org/networking/skbuff.html)

## 先读三个源码坐标

| 文件与入口 | 带着什么问题看 | 别急着推出的结论 |
| --- | --- | --- |
| `net/ipv4/ip_input.c` / `ip_rcv()` | IPv4 输入如何进入后续处理？ | 到这里就已完成全部 IP 处理 |
| 同文件 / `ip_local_deliver()` | 本地交付如何继续交给上层协议？ | 任意用户进程已经读到数据 |
| `net/ipv4/ip_forward.c` / `ip_forward()` | 转发检查与后续发送怎样衔接？ | 转发必须经过业务 Socket |

源码可直接对照 [v6.6 ip_input.c](https://github.com/torvalds/linux/blob/v6.6/net/ipv4/ip_input.c) 和 [ip_forward.c](https://github.com/torvalds/linux/blob/v6.6/net/ipv4/ip_forward.c)。这里列的是定位入口；路由结果、Netfilter 钩子和继续执行的回调，需要放在一起看。

## 同一台网关，为什么会看到两种行为

发给本机 IKE 服务的 UDP 报文，需要到达守护进程的 Socket。网关替两端主机转发的业务包，则可能根本没有一个本机业务 Socket 与它对应。于是，“应用没读到包”在后一种场景里可能是问错了对象。

本机主动发出的包还有本地输出路径，也不能简单套用接收方向的 FORWARD 检查。我的阅读习惯是先把流量写成一句话：**谁发给谁，在哪个命名空间，属于本地输入、本地输出还是转发。** 再决定看 Socket、路由还是转发策略。

## 观察点要能回答一个小问题

| 问题 | 可以先观察什么 | 仍然不能单独证明什么 |
| --- | --- | --- |
| 接口有没有流量？ | 接口包数、错误和丢弃计数 | 包已经被应用接受 |
| 为什么走这个出口？ | 对应命名空间、地址与 mark 下的路由选择 | 防火墙和后续封装一定放行 |
| 是否到了本机传输层？ | Socket 状态、协议统计、合适的跟踪点 | 用户态处理已经成功 |
| 哪层开始拥堵？ | 队列、CPU 分布、函数采样 | 一个热点计数就足以定因 |

这些是待执行的观察计划，不是本篇的实验输出。后续若加入 eBPF 跟踪，应固定内核版本与实际函数路径，并考虑聚合、采样和卸载对观测的影响。
