沿着内核、IPsec 和 OpenVPN 看过一圈，最后总会回到同一个问题：慢在哪里？我现在更愿意先写测量条件，而不是先选一种加速技术。

**这篇是一份性能研究方法与待执行计划，不是基准测试报告。** 目前没有可以放进本文的吞吐、PPS 或 P99 实测结果。下面所有对照项都是实验设计，不是已经获得的收益。

## “VPN 性能”至少包含三件不同的事

| 测量对象 | 指标 | 可能相关的路径 |
| --- | --- | --- |
| 建立与维护连接 | 建链速率、握手时延、重协商耗时 | IKE / TLS、认证、证书、密钥交换 |
| 稳态业务传输 | 吞吐、PPS、每核负载、错误率 | XFRM / ESP 或 OpenVPN 实际数据通道 |
| 压力下的响应 | P50 / P95 / P99、丢包、排队 | 队列、调度、批处理、拥塞与应用 |

握手慢与传输慢，不应共用一个未经验证的解释。把证书操作优化得更快，也不能直接推出稳定传输时的逐包路径变快。

## 建立一份能重复的负载描述

我会先固定软件版本、算法与模式、CPU／网卡、卸载状态、MTU、流向、流数、业务包长、持续时间和预热方式。记录中还要说明字节数算在应用层、IP 层还是链路层，避免两个“Gbps”其实不是同一种口径。

包长尤其容易掩盖问题。相同字节速率下，小包意味着更多次逐包处理；因此只测一种大包吞吐，可能看不到查表、分配或队列操作的固定成本。这是设计测试矩阵的理由，不是当前系统已存在某个瓶颈的结论。

```text
待执行矩阵（不含测量结果）
工作负载：单流 / 多流 × 多种业务包长
运行路径：普通转发 / 指定 VPN 数据面
共同条件：版本、算法、MTU、核数、持续时间、卸载状态
同时记录：吞吐、PPS、尾时延、每核 CPU、丢弃与错误
```

## 按同一段时间，把四组观察对上

RSS、RPS、RFS 和 XPS 分别涉及不同位置的队列与 CPU 分配。它们提供并行处理的手段，也可能引入额外中断、跨核交接和缓存成本。看到单核很忙时，先核对流量分布和 IRQ／队列关系；“把所有核都打开”本身不是验收标准。[Linux 网络扩展性文档](https://docs.kernel.org/networking/scaling.html)

NAPI 的预算和批处理行为也会影响观察。某个软中断线程负载高，需要结合吞吐、排队和丢弃解释。单独一张 CPU 截图，既不能证明瓶颈，也不能证明系统已经得到有效利用。[NAPI 文档](https://docs.kernel.org/networking/napi.html)

## 工具按问题选，不按名字堆

| 我想回答的问题 | 可选观察工具 | 解释边界 |
| --- | --- | --- |
| 流量是否偏向某个队列／核？ | ethtool、IRQ 计数、每核 CPU 统计 | 驱动统计字段与含义需核对 |
| CPU 时间花在什么函数？ | perf 采样与符号栈 | 采样频率、符号和权限会影响结果 |
| 某个路径发生多少次、多久？ | 合适的 tracepoint / eBPF 程序 | 跟踪本身有开销，内核接口有版本差异 |
| 是否真的进入 IPsec？ | SA 增量、策略与内外侧抓包 | 相关性要限定在同一条测试流 |

这里没有给出一套直接对生产环境执行的调优命令。先在独立环境选择一个观察问题，保存原始输出，再逐步扩大测量范围。

## 高速路径是带着条件的候选项

XFRM offload、OpenVPN DCO、XDP / AF_XDP 和 DPDK 面向的接入点与职责并不相同。换掉一段数据路径，通常还要回答密钥更新、路由、防火墙、异常回退、驱动兼容和观测怎么接回去。

我会用一个很朴素的判断：**当前证据指向哪段成本，这个方案是否恰好减少它，又把什么责任交给了我？** 若还没有 Profile，就先不声称需要重写数据面。

## 下一篇真正的性能文章应带来什么

一套独立可公开的环境、一份基线、一个明确假设、一组单变量对照，以及原始数据和复现步骤。没改善也值得写：它排除了什么，比一个脱离条件的“提升百分比”更有帮助。
