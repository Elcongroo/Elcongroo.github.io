## 1. 体系要解决什么

验收不能只问“功能能不能用”，也不能只检查“有没有某个文件”。每个关键能力都要闭合下面这条链：

```mermaid
flowchart LR
    A["标准/采购要求"] --> B["协议或产品功能点"]
    B --> C["配置与运行入口"]
    C --> D["源码文件、函数和分支"]
    D --> E["正向与负向用例"]
    E --> F["日志/PCAP/系统状态/测试结果"]
    F --> G["通过、缺陷、待确认及边界"]
```

到货前，`D`中的供应商位置和`F`中的产品结果允许为空；其余字段应先定义好。这样代码到货后做的是“逐项填空和验证”，而不是漫无目的浏览目录。

## 2. 标准范围怎样拆

| 来源 | 当前先转成哪些检查域 | 到货后的重点 |
| --- | --- | --- |

| GM/T 0023-2023 | 功能、性能、安全管理 | NAT-T、认证、防重放、重协商/更新、探测、吞吐/时延/丢包/建链与并发 |
| GM/T 0024-2023 | TLCP握手、记录层、密钥计算 | 状态机、双证书、密码套件、会话密钥和记录层 |
| GM/T 0025-2023 | SSL VPN网关产品要求与测试 | 用户接入、业务转发、性能、安全和管理功能 |
| GM/T 0026-2023 | 安全认证网关部署、功能、性能和安全 | UKey/证书认证、访问控制、代理转发、审计和管理 |
| 采购要求 | 源码来源、构建、可维护性、HSM/PQC可扩展 | 文件/模块来源、依赖许可、可重复构建、密码适配层和Dummy扩展 |

这里是“接管工作矩阵”，不是代替检测机构的完整认证用例。精确到每个子条款的合规结论，必须以获授权的标准全文、产品形态和检测规则为准。

## 4. 每一行怎么判定

每行只能使用以下结果：

- `通过`：源码路径、运行路径和正/负向结果闭环；
- `有缺陷`：目标能力存在，但结果与标准或约定不一致；
- `待确认`：材料不足，不能将“看起来可能支持”写成通过；
- `不适用`：必须写明产品边界和双方确认依据；
- `未交付`：源码、依赖、文档或测试资料缺失。

判定时至少回答四个问题：

1. 这段代码是否进入实际构建产物？
2. 运行的是否是该产物，而不是系统旧版本？
3. 请求是否真的经过该分支？
4. 错误输入是否会安全失败，而不是静默回退？

## 5. 到货后的填写顺序

```text
冻结介质Hash/版本
→ 建模块清单和来源清单
→ 先完成独立构建与运行身份确认
→ 从配置或PCAP反向追真实执行链
→ 将真实文件/函数填入矩阵
→ 运行正向和负向用例
→ 保存原始证据与Hash
→ 形成通过/缺陷/待确认清单
```

不要先把整仓库读一遍。围绕矩阵中的高风险链逐条进入源码，效率和可审查性都更高。
