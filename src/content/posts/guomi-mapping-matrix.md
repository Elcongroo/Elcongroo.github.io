## 1. 文档目的

本文用一张表回答一个具体问题：上游（OpenVPN / strongSwan / 密码库 / 内核）的每项能力，为实现国密需要在哪个改造点、哪一层落笔。

本文是理解产品内部国密改造的「地图」：接手已国密化的 OEM 网关时，用这张表定位产品可能的改造点，再去源码 / 抓包核查产品是否真的这样实现。每行的「当前理解状态」由对应专项文档的研究结果驱动更新。

## 2. 使用说明

### 2.1 列的填写要求

| 列 | 填写要求 |
| --- | --- |
| 上游系统/协议 | 只写系统或协议名，不写版本号以外的推断 |
| 上游能力或算法 | 写上游实际使用的能力。未核对源码前标注「待核对」 |
| 国密改造点 | 写为实现国密需要落笔的位置，不写实现细节 |
| 涉及模块 | 只写功能模块名。文件路径与函数名在源码确认后由源码导览承载 |
| 改造点所在层 | 写改造点落点的层级，优先填扩展点、插件点、后端或抽象层 |
| 当前理解状态 | 只能取第 2.2 节定义的值 |
| 核查方式 | 必须给出可执行的核查手段，不能写「待确认」 |
| 风险 | 写该改造点特有的风险 |
| 对应文档 | 指向承载该行研究的专项文档 |

### 2.2 理解状态取值

| 状态 | 含义 |
| --- | --- |
| 待理解 | 尚未开始 |
| 线索阶段 | 只有第三方资料或推测，未独立验证 |
| 已定位改造点 | 已通过上游源码确认改造落点 |
| 已核查产品实现 | 已在产品源码 / 抓包中核查该改造点的实际实现 |
| 已评测 | 已通过实验或抓包验证产品实现符合国密 |

### 2.3 两条填写纪律

1. 未核对源码前，「上游能力或算法」一列必须保留「待核对」标注。不同版本的能力集合不同，不能凭记忆填写。
2. 本表不填文件路径与函数名。这类信息只写进源码导览或上游源码研究文档，并标注证据来源。

## 4. 更新规则

1. 每行的状态变更必须由专项文档中的证据驱动，并在专项文档中注明证据来源。
2. 同一行状态升级时，在对应专项文档中保留旧状态与升级原因。
3. 当一行涉及方案选择时，按《GM-VPN 技术文档写作规范》第 17 章创建相应 ADR。
4. 新增行的顺序：先归入已有系统或协议分组，不另起新分组。

1. 继续完成 OpenVPN/TLCP、密码库和目标内核能力核对。
