## 先分开三个“成功”

一个管理接口返回成功，至少可能表示三件不同的事：配置已持久化、守护进程接受了新配置、目标业务已经按新配置运行。把三者压成一个绿色状态，故障发生时就无法知道停在哪里。

RFC 8342 的 NMDA 模型区分配置意图与设备实际使用的运行状态。本文借用这个区分建立阅读坐标，并不要求某个网关必须实现 NETCONF 或采用同名数据库。[RFC 8342 §5](https://www.rfc-editor.org/rfc/rfc8342.html#section-5)

以下接口、版本号与流程均为**设计示例，尚未实现或实测**。

## 配置有版本，运行结果也要有归属

```mermaid
flowchart LR
  A["配置 v17<br/>身份与参数校验"] --> B["应用计划<br/>差异与依赖"]
  B --> C["VPN adapter<br/>加载与发起"]
  C --> D["实际 IKE SA / CHILD SA"]
  D --> E["观测快照<br/>关联 v17"]
  E --> F["确认 / 超时 / 补偿"]
```

可以把一个应用请求表示为 `Apply(config_version, request_id, expected_previous_version)`。最后一个字段用于拒绝覆盖别人刚刚提交的修改；`request_id` 用于识别网络重试。它们不是某个现有产品的 API，而是审查接口时值得追问的约束。

运行状态中至少保存期望版本、最近尝试版本、已观察到的版本、尝试结果与时间。不能仅凭“读取配置文件的版本号”填充已生效字段：守护进程可能接受配置，但旧 SA 仍在承担业务。

## 为什么数据库事务包不住整条链

配置写入数据库、证书文件替换、VICI 加载、路由更新和内核 SA 安装，通常不处于同一个事务中。数据库回滚不会自动删除已安装的策略，也不会恢复已断开的会话。

设计时可以先划分四段：准备与校验、执行差异、观察收敛、失败补偿。每一段分别列出可重复操作、不可逆影响和恢复办法。例如“重新加载同一份连接配置”与“立即删除当前 IKE SA”对现有业务的影响显然不同。幂等也不等于零影响：重复执行一个删除请求，仍可能中断后来建立的新连接，所以还需要对象身份和代次约束。

| 交接 | 接收方必须返回什么 | 不能由此推出什么 |
| --- | --- | --- |
| API → 配置存储 | 校验结果、配置版本 | 守护进程已读取 |
| 配置存储 → VPN adapter | 应用请求 ID、具体差异 | 对端接受算法 |
| adapter → 协议栈 | 加载与发起的分别结果 | 新 CHILD_SA 已有流量 |
| 协议栈 → 观测 | SA 身份、SPI、方向、计数与时间 | 所有业务目标都满足 |

## 回滚要恢复哪一层

NETCONF 的 confirmed commit 提供一个有用的参照：变更必须在窗口内确认，否则恢复此前配置；它也定义了会话中止、持久确认和重启相关行为。它的能力依赖和协议语义不能直接套成一个普通 REST 接口的保证。[RFC 6241 §8.4](https://www.rfc-editor.org/rfc/rfc6241.html#section-8.4)

对 VPN 管理链而言，我会把“恢复配置”“恢复可管理性”“恢复业务”设为三个验收项。恢复旧配置后，对端会话、连接计数和重连时间未必回到旧值。也不要恢复旧 SA 的序列号或会话密钥来伪装成无损回滚；会话生命周期要由协议与数据面一致处理。

一个值得单独测试的场景是：新防火墙或路由配置切断了管理连接。恢复动作不能完全依赖刚被切断的那条连接。是否使用本地定时恢复、带外管理或另一条管理路径，需要在实际平台上选择并验证。

## 怎样接回现有源码笔记

[配置到 IKE_SA](/articles/strongswan-config-ike-sa/)描述 VICI 配置对象进入运行连接的链路；[CHILD_SA 到 XFRM](/articles/strongswan-child-sa-xfrm/)描述协商结果进入内核的链路。管理系统应分别观察这些交接，而不是用一个“服务进程存在”代替它们。

对 OpenVPN，则沿[配置到运行上下文](/articles/openvpn-config-context/)核对哪些配置只在启动时读取，哪些变化需要重连或重启。没有读过具体版本的重载行为，不能承诺所有配置热更新。

## 尚待验证：一次失败恢复演练

在独立实验环境中先保存旧配置与外层可达性，再做以下四种注入。这里列出的是测试计划，没有通过结果。

1. 提交格式合法但双方无共同 Proposal 的配置：管理面应显示协商失败及对应版本，不能显示“已生效”。
2. 在配置持久化后、下发前终止应用进程：重启后能定位未完成请求，并按约定重试或取消。
3. 重复发送相同请求：不应产生无法解释的多份连接、路由或 SA。
4. 在应用后切断管理路径：观察定时恢复能否执行，以及旧业务需要多长时间重新收敛。

验收材料包括配置版本、应用事件、进程身份、SA 与策略变化、业务探测和恢复后的状态。不把“最后又能 Ping 通”当作整条事务已正确实现的证明。
